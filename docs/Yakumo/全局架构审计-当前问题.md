# Yakumo 全局架构审计：当前问题

审计日期：2026-09-05

## 整改复核更新（2026-09-06）

以下正文保留初始审计基线，不应将其中的迁移前描述视为当前代码状态。
第一阶段以 [架构整改实施记录](架构整改实施记录.md) 的 P1 Turn state 收敛为准，
不是本文后面的建议优先级 P1，也不代表整个目标架构已经完成。

- 已迁移的输入/STT、Router、Planner、Expression、完成状态、Conversation 提交和

  已迁移字段仍有两个内部事实源。

- Output Runtime 公共契约、Agent 拆分、Capability 模型关系及真实平台并行插件验收
  仍未完成；Runtime observation 适配标记也不能仅因名字相似就当作已迁移字段。
- 本次收尾新增边界用例并运行针对性检查：3 个分支测试、6 个完成通知/hook 测试通过；
  Ruff 通过。此前 123 passed 是上一批验证记录，不能替代真实平台端到端验收。

## 1. 审计范围

本审计以以下材料为依据：

- 当前 AstrBot 代码仓库的实际调用关系
- `docs/Yakumo` 下的设计、当前状态和迁移文档
- `AG99live` 的 `interaction-evolution.md`
- 附件中提出的全局架构审计标准

本文件记录当前问题和结构风险，不是改造方案，也不代表所有问题都已经通过真实平台运行验证。

## 2. Executive Summary

当前项目不是需要推倒重写的系统，但已经出现明显的架构漂移和增量开发债务。

总体判断：

> Architecture Drift + Accumulated Incremental Debt + Needs Structural Refactoring

主要问题：

1. `AstrMessageEvent` 被整个系统当作跨层可变上下文使用，而不仅是平台事件接口。
2. Interaction Middleware 仍承担输入、路由、输出拦截、生命周期和兼容衔接。
3. `astr_main_agent.py` 仍同时装配 Agent、Prompt、Capability、Provider 和 Execution。
4. 输出生命周期跨多个协作组件，边界复杂，但目前不足以证明它们错误地共同拥有同一状态。
5. Agent、Prompt、Capability、Execution 之间存在多套相关模型，转换和同步成本较高。
6. 并行插件运行时默认关闭，文档目标状态与默认生产路径之间仍有偏差。

当前最值得处理的区域：

1. `event.extra` 内部状态的清点和收敛。
2. `InteractionMiddleware` 与 `astr_main_agent.py` 的职责缩小。
3. 输出协作组件的状态边界和唯一写入规则。
4. Capability / Execution / ProviderRequest 模型关系的明确化。

## 3. 实际架构地图

### 3.1 启动链路

```text
main.py
  -> InitialLoader.start()
  -> AstrBotCoreLifecycle.initialize()
  -> AstrBotCoreLifecycle.start()
  -> PipelineScheduler
  -> PlatformManager / EventBus
  -> Platform Adapter
```

主要文件：

- `main.py`
- `astrbot/core/initial_loader.py`
- `astrbot/core/core_lifecycle.py`

`AstrBotCoreLifecycle` 目前直接装配 Provider、Platform、Conversation、Persona、
Plugin、Pipeline、Memory、Interaction、Personal Runtime、Cron、Knowledge Base、
SubAgent、Dashboard 和输出生命周期组件，是当前最大的中心装配点。它值得继续
收敛，但当前代码证据不足以证明它已经承担了大量业务决策；更准确地说，它是
`QUESTIONABLE` 的装配中心，而不是已确认的首要缺陷。

### 3.2 普通请求链路

```text
Platform Adapter
  -> EventBus
  -> PipelineScheduler
  -> ProcessStage
  -> Plugin Handler discovery
  -> Interaction Middleware
  -> Personal Runtime / Router
  -> AgentRequestSubStage
  -> astr_main_agent
  -> Prompt Collectors
  -> ContextPack
  -> Prompt Projection / Renderer
  -> ProviderRequest
  -> Provider / Tool Loop
  -> Output Controller
  -> Platform Adapter
  -> Conversation / Postprocess / Memory
```

### 3.3 并行插件链路

```text
ProcessStage
  -> InteractionTurnCoordinator
  -> PluginExecutionRuntime
  -> Plugin Job
  -> Plugin Gate
  -> T1 Personal / Core
  -> T1 settlement
  -> T2 delayed delivery
  -> Plugin artifact delivery
```

该路径由 `parallel_plugin_runtime_enabled` 控制，默认值为 `False`。
因此文档中的并行插件运行时目前不是默认生产路径。

## 4. 关键问题

### 4.1 Interaction Middleware 职责过宽

位置：

- `astrbot/core/interaction/middleware.py`

实际职责同时包括：

- 输入物化和 STT
- ContextPack 准备
- Router
- Persona 表达
- Core Planner
- 输出拦截和输出持久化
- 生命周期事件
- 插件兼容
- Postprocess 衔接
- fallback

这已经超出单纯的 Persona Runtime Shell。一次 turn 的编排复杂度是真实的，
但当前实现还把输入、决策、输出、状态和持久化职责集中在同一个 Middleware 边界内。

判断：`HIGH`（`CONFIRMED`）

建议方向：保留 Middleware 作为 turn orchestrator，但将输入、路由、Core
执行、Output 和持久化改为明确端口。

### 4.2 `event.extra` 仍是第二状态容器

位置：

- `astrbot/core/interaction/middleware.py`
- `astrbot/core/platform/astr_message_event.py`
- `astrbot/core/interaction/turn_state.py`

当前同时存在：

```text
InteractionTurnState
  + event.extra
  + PersonalRuntime state
  + PluginBranchResult
  + PluginExecutionRuntime state
```

Middleware 仍通过 `_interaction_*` extra 保存原始发送方法、输出控制器、路由、
状态和兼容信息。文档虽然声明 typed state 是主事实源，但内部主链路并未完全达到
这个状态。

风险：

- 状态被不同模块分别读取和修改
- 事件复用或重复包装时产生隐式状态污染
- 取消、迟到输出和完成状态难以证明一致

判断：`HIGH`（`CONFIRMED`）

### 4.3 Output Gateway 尚未真正收口

在 `middleware.py` 中，Interaction 仍然通过 `MethodType` 替换：

- `event.send`
- `event.send_streaming`
- `event.complete_visible_turn`

并把原始方法写入：

- `_interaction_original_send`
- `_interaction_original_send_streaming`
- `_interaction_original_complete_visible_turn`

当前输出链路同时涉及：

```text
AstrMessageEvent
  -> MethodType wrapper
  -> InteractionOutputController
  -> PluginArtifactDeliveryCoordinator
  -> DelayedPluginDeliveryCoordinator
  -> TurnDeliveryCoordinator
  -> Platform Adapter
```

这些对象分别参与输出捕获、身份判断、artifact 处理、发送、历史提交和完成通知。
当前可以确认输出生命周期跨越多个协作组件，且 Middleware 仍通过方法替换介入；
但仅凭静态代码不能证明这些组件错误地共同拥有同一份状态，也不能直接断言已经
产生重复发送或状态错误。应优先核对各组件的写入边界和 ledger 关系。

判断：`MEDIUM/HIGH`（`CONFIRMED boundary complexity; defect NEEDS VERIFICATION`）

### 4.4 T1/T2 与迟到输出存在需要验证的竞态

位置：

- `astrbot/core/pipeline/process_stage/stage.py`

插件完成回调在等待 `t1_settled` 后执行延迟投递，随后清理 delivery records。
在 `HANDLED` 或 `STOPPED` 路径中，T1 已经交付产物并停止事件，但 Handler 可能仍
继续产生后续产物。

需要证明：

- T1 结束后迟到产物一定不能重新取得发送权
- 旧 turn 的输出不能复活
- T2 delivery 不会重复写历史
- STOPPED 不会被误解为空产物

目前静态代码和单元测试不足以证明所有这些端到端条件。

判断：`NEEDS VERIFICATION`，潜在风险 `MEDIUM/HIGH`

### 4.5 Agent 构建中心过重

位置：

- `astrbot/core/astr_main_agent.py`

当前同时处理：

- Provider 选择
- Conversation 获取
- Persona 解析
- Prompt Context 装配
- Capability 装配
- 工具注册
- Provider fallback
- `ProviderRequest`
- `CoreExecutionSpec`
- Agent Runner
- 生命周期和错误处理

该文件实际上同时承担 Agent Kernel、Agent Platform、Prompt Assembly 和
Capability Assembly 的职责。

判断：`HIGH`（`CONFIRMED`）

### 4.6 Capability / Execution 模型并行存在

当前相关模型包括：

- `ToolSet`
- `CapabilitySnapshot`
- `CoreCapabilitySnapshot`
- Prompt `tool_schema`
- 全局 `llm_tools`
- `CoreExecutionSpec`
- `ProviderRequest`

这些模型分别表达可执行工具、模型可见 schema、Core 能力、Provider 请求和插件注册，
但边界仍然通过转换和同步维持。

风险：

- 模型可见工具与实际可执行工具不一致
- fallback 或重渲染时能力快照失效
- 同一工具在不同路径出现不同 schema
- 未来 Backend 适配需要维护更多转换层

判断：`MEDIUM/HIGH`（`CONFIRMED model-conversion cost; semantic duplication not proven`）

### 4.7 并行插件路径默认关闭

配置位置：

- `astrbot/core/config/default.py`

当前：

```text
parallel_plugin_runtime_enabled = False
```

因此文档中关于 Plugin Job、T1/T2、窗口 watcher、迟到 Handler 和后台 completion
的设计，并非默认主链路行为。

代码中已经存在较完整的 runtime gate、delivery ledger、reservation 和 T1 boundary
保护，因此这里首先是“目标路径尚未成为默认路径”的架构状态问题，而不是已确认的
并行运行时缺陷。除非完成真实平台验收，否则不能判断旧串行路径是否可以删除，也不能
把并行路径视为已完成架构。

判断：`NEEDS VERIFICATION`

### 4.8 Turn、Task、Job、Execution identity 需要语义核对

当前存在：

- `turn_id`
- `run_id`
- `job_id`
- `execution_id`
- `message_id`
- `conversation_id`

这些标识各自可能有合理用途，当前不能仅凭数量认定为重复或错误；仍需核对父子
关系、恢复语义和取消归属。
尤其是取消、插件后台任务、Core 执行、输出 artifact 和 Conversation 提交之间，
容易出现“同一业务轮次多个 owner”的问题。

判断：`NEEDS VERIFICATION`

### 4.9 Personal Runtime 边界总体较成熟

代码中已经存在 `PersonalRuntimeManager`、`PersonalState`、Observation Inbox、
Wake Scheduler、cooldown 和 proactive state 等明确组件。它们说明 Persona 连续
状态并非简单散落在 Middleware 中。

当前更准确的判断是：Personal Runtime 具有可保留的 owner 和生命周期边界，
后续重点应放在它与 `event.extra`、Conversation、输出完成反馈之间的接口收口，
不应与方法替换或全局可变事件上下文放在同一级严重度。

判断：`GOOD WITH BOUNDARY WORK`

## 5. 第二轮代码复核与结论修订

本轮复核以实际代码为准，重点检查第一轮报告中容易过度推断的结论。

### 5.2 本轮降级或改写

| 第一轮表述 | 复核后的表述 | 原因 |
|---|---|---|
| 多个输出 owner 已经造成错误架构 | 输出生命周期跨多个协作组件，边界复杂；是否存在错误的共同状态 owner 仍需验证 | `InteractionOutputController`、artifact delivery、delayed delivery、`TurnDeliveryCoordinator` 和事件发送接口有不同职责 |
| T1/T2 迟到输出存在竞态 | T1/T2 迟到输出是需要端到端验证的风险 | 已发现 delivery key、ledger、reservation、duplicate fingerprint 和 T1 boundary freeze 等保护 |
| Turn、Task、Job、Execution identity 过多是问题 | 标识较多，是否语义重叠需要核对 | 当前尚未证明父子关系无法恢复或取消归属不明 |
| Prompt 系统接近过度工程 | Prompt 复杂度较高，有继续膨胀风险；暂不能证明明显过度工程 | 多 Provider、工具协议和 exposure 控制带来合理复杂度 |
| Execution Backend 抽象是过度工程 | `CoreExecutionSpec` 仍有内部事实边界价值，是否需要 Backend 抽象取决于第二个真实后端 | 当前不能以“尚无第二个后端”直接否定该边界 |
| `AstrBotCoreLifecycle` 是大型业务决策中心 | 它是大型装配中心，但是否承担过多业务决策仍属 `QUESTIONABLE` | 需要继续按装配与决策调用图拆分核对 |

### 5.3 全局性修正

第一轮把问题主要描述成 Interaction 的 `event.extra` 泄漏，这还不够准确。
更完整的结论是：

> `AstrMessageEvent` 已被整个系统当作跨层可变上下文使用，而不是仅作为平台事件
> 和发送接口。`event.extra` 因而同时承载运行时状态、请求事实、Prompt 结果、
> 执行规格、停止信号和兼容标记，形成跨层隐式协议。

这比“Interaction 有一个第二状态容器”更广，也意味着治理范围不能只停留在
`interaction/` 目录内部。

## 6. Architecture Drift

| 设计目标 | 实际代码 | 偏差 |
|---|---|---|
| Interaction 是 Persona Runtime Shell | 同时承担输入、输出、路由、生命周期和持久化 | Middleware 过宽 |
| typed state 是唯一内部事实源 | `event.extra` 仍参与主链路 | 双重事实源 |
| Output Gateway 统一输出 | `MethodType` 仍替换事件方法 | 兼容方案仍在主路径 |
| Agent 只负责编排 | `astr_main_agent.py` 直接装配大量能力 | Kernel 与 Platform 混合 |
| Capability 有统一快照 | 多套 Tool/Capability/schema 模型并存 | 能力边界未统一 |
| CoreExecutionSpec 是执行边界 | 仍主要是进程内事实模型 | 尚未成为统一 Backend 协议 |
| 并行插件运行时可用 | 默认开关关闭 | 新路径尚未成为默认行为（已确认） |
| Persona 与 Conversation 分离 | 两者仍通过部分上下文和完成反馈协作 | 边界需继续核对，不能直接判定为错误 |

## 8. 概念漂移

| 规范概念 | 当前名称 | 冲突 | 建议名称 |
|---|---|---|---|
| 一次交互 | event、turn、interaction turn、runtime turn | 范围不同但命名相近 | `InteractionTurn` |
| 核心执行 | Agent run、Core run、Provider request、Execution spec | 运行、请求、执行混用 | `CoreExecution` |
| 能力集合 | ToolSet、CapabilitySnapshot、tool schema、llm_tools | 可见能力和执行能力混用 | `CapabilitySnapshot` + `ExecutableToolSet` |
| 输出 | send、emit、artifact、delivery | 意图、产物、送达混用 | `OutputIntent -> OutputArtifact -> Delivery` |
| 人格表达 | Persona、Expression、Personal、visible reply | 人格数据和表达动作混用 | `PersonaState` / `PersonaExpression` |
| 上下文 | Context、ContextPack、Prompt context | 运行上下文和模型上下文混用 | `RuntimeContext` / `PromptSnapshot` |
| 插件执行 | Handler、Job、Branch、Invocation | 注册、执行、分支混用 | `PluginInvocation` |

## 9. 复杂度热点

### 9.1 Interaction Middleware

必要复杂度：一次 turn 确实需要协调输入、Persona、Router、Core 和 Output。

偶然复杂度：方法替换、extra 状态、旧流程兼容、输出持久化和生命周期都集中在同一层。

建议：只保留 turn 编排，把输入、决策、执行、输出和持久化变成明确 owner。

### 9.2 `astr_main_agent.py`

必要复杂度：构造一次 Core Agent。

偶然复杂度：Provider、Conversation、Prompt、Capability、Tool、fallback、Execution
全部在一个模块中装配。

建议：将其收敛为 `CoreExecutionAssembler`，Provider 和 Capability 通过明确端口注入。

### 9.3 Output Controller 与 Delivery Coordinator

必要复杂度：输出确实需要区分 intent、artifact、送达和完成。

偶然复杂度：多个类共同拥有这些状态，并通过 event extra、ledger 和 reservation 协调。

建议：保留一个 Output Runtime，其他 coordinator 变成其内部策略或阶段实现。

### 9.4 Prompt 系统

多 Provider、工具协议和 exposure 控制带来的复杂度是合理的，不能仅凭类和
模型数量判定为过度工程。

但当前 `Slot`、`Target`、`Exposure`、`Placement`、`Layout`、`Profile`、`Catalog`、
`Budget`、`Renderer` 已接近一套独立 DSL。后续不应继续新增 Prompt 抽象，应先清理
迁移残留并固定概念边界。判断：`QUESTIONABLE / NEEDS VERIFICATION`。

## 11. 抽象层审计

| 抽象 | 实际价值 | 判断 |
|---|---|---|

## 12. 状态所有权审计

| 状态 | 当前 owner | 其他写入者 | 问题 |
|---|---|---|---|
| Interaction turn | `InteractionTurnState` | `event.extra`、Middleware | 双写 |
| Route decision | Router / TurnState | Middleware、ProcessStage | 镜像字段 |
| Personal session | `PersonalRuntimeManager` | Conversation、Middleware | episode 与人格边界需继续收口 |
| Conversation | `ConversationManager` | Core、Output、Postprocess | proactive/assistant-only 规则复杂 |
| Agent live state | Runner / Agent Context | event extra、Execution Ledger | 运行状态和审计记录边界需核对 |
| Plugin task | Plugin Runtime / Coordinator | Branch、ProcessStage | owner 不完全明确 |
| Observation | Inbox / PersonalState | Heartbeat、Wake Scheduler | 生命周期复杂但主 owner 基本明确 |
| Prompt context | ContextPack | event extra、ProviderRequest | snapshot 与 request 存在复制 |
| Memory | Memory Service | Conversation/Postprocess | 需要严格只读 Snapshot 边界 |
| Runtime config | Config Manager | event extra、merge helper | 局部 fallback 较多 |
| Model config | ProviderManager / ProviderRequest | Main Agent、fallback resolver | Provider selection 与请求构建耦合 |

## 15. 推荐目标结构

不建议重写。建议逐步收敛到：

```text
Platform Adapter
  -> Event Intake
  -> TurnContext
  -> Interaction Orchestrator
       -> Input Port
       -> Route Port
       -> Persona Runtime Port
       -> Core Execution Port
       -> Output Runtime Port
  -> Persistence Ports
       -> Conversation
       -> Memory
       -> Execution Ledger
```

核心 owner：

- `InteractionOrchestrator`：只负责本轮阶段协调
- `PersonalRuntime`：Persona 连续状态和 Observation
- `Router`：只做路由
- `Planner`：只做 Core 执行决策
- `CoreExecutionAssembler`：生成执行事实、Prompt Snapshot 和 Capability Snapshot
- `AgentRunner`：模型和工具循环
- `OutputRuntime`：输出意图、产物、送达和完成
- `ConversationStore`：Conversation episode
- `MemoryService`：长期记忆和只读 Snapshot
- `ExecutionLedger`：Core 执行审计

## 18. Final Verdict

### 第一件应治理的东西

先冻结、分类并迁移已经被 TurnState 覆盖、但仍通过 `event.extra` 传递的内部状态；
在完成调用者和兼容验证前，不应直接删除。

### 第一件应收敛的东西

收敛 OutputController、Plugin Artifact Delivery、Delayed Delivery 和
Turn Delivery 的公共状态边界与写入规则；是否物理合并类，取决于调用图和端到端验证。

### 最大架构风险

`AstrMessageEvent` 被跨层作为可变上下文使用，导致 TurnState、事件 extra、执行事实
和输出生命周期之间存在隐式耦合。

### 最值得保留的设计

Persona Runtime 与 Core Execution Ledger 的分离。

### 最明显的复杂度风险

围绕 Capability、Prompt、Execution 和多阶段 Output Runtime 形成的多层转换与兼容结构；
其中 Execution Backend 本身暂不能判定为过度工程。

### 如果只能做三件事

1. 建立清晰的 OutputRuntime 状态边界和唯一写入规则。
2. 清理 `event.extra`，让 TurnContext/TurnState 成为内部主事实源。
3. 收敛 Capability / Execution / ProviderRequest 的关系，并缩小 `astr_main_agent.py`。

## 19. NEEDS VERIFICATION

以下结论不能仅凭当前静态阅读完全证明：

- T1/T2 迟到插件输出在所有平台上都不会复活旧 turn。
- 插件 Handler、输出等待和外部等待是否完整纳入同一个 Turn Deadline 预算。主要
  Interaction/Core 阶段已经使用统一 `TurnDeadlineBudget`，因此问题不是“完全没有
  deadline”，而是覆盖边界仍需核对。
- 并行插件路径在真实私聊、群聊和插件 reload 场景中可以替代串行路径。
- 外部插件是否仍依赖部分 `event.extra` 和旧输出方法。
- 历史配置和 Provider fallback 分支是否仍有真实消费者。
- Prompt 旧入口是否存在仓库外调用者。
- Turn、Task、Job、Execution identity 是否存在实际语义重叠或取消归属问题。
- 是否存在第二个真实 Execution Backend，足以 justify 更强的 Backend 抽象。

需要的证据：

- 真实平台日志
- 端到端输出链路测试
- 插件兼容性样本
- 全仓库和外部插件调用图
- 取消、超时、fallback、reload 和重复投递场景的运行记录

## 20. 本轮复核结论

本次复核没有发现需要立即修改业务代码的、能够由静态检查直接证明的单点缺陷；
发现的是多个已经存在的架构边界问题和若干需要运行时证据才能定性的风险。

因此当前报告的优先级应理解为：

1. 先治理跨层可变事件上下文和 Middleware 方法替换。
2. 再收敛 Agent 装配与 Capability/Execution 模型关系。
3. 同步对输出协作组件、并行插件路径和 deadline 覆盖做端到端验证。
4. 在验证前，不删除官方事件 API、旧串行路径、ProviderRequest 或 CoreExecutionSpec。
